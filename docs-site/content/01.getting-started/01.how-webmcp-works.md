# How WebMCP Works

WebMCP lets a compatible browser expose useful actions and information from your
application to an agent. Your application remains a normal application first:
when the browser does not provide WebMCP, the page continues to work.

## What the browser provides

The default environment calls `globalThis.document?.modelContext` when a
controller starts. A context must provide `registerTool(tool, options?)`.
The controller also uses `unregisterTool` if available for cleanup; otherwise,
the registration `AbortSignal` is the baseline cleanup mechanism. The
`ModelContextLike` interface also includes `getTools`, `executeTool`, and
`toolchange` for completeness, but this library's lifecycle management does
not call them.

::note{icon="i-lucide-globe"}
**Runtime capability.** The library does not use browser-version detection. A
browser or origin either provides the runtime capability when discovery occurs,
or it does not.
::

## What happens when it is unavailable

An unsupported browser is a normal state. A controller starts with
`{ supported: false, registered: false, error: null }`; if no capability appears
before the discovery timeout, `error` becomes a `ToolTimeoutError` while
`supported` remains `false`. This diagnostic does not mean the application is
unsupported or should stop rendering.

::tip{icon="i-lucide-lightbulb"}
Keep the visible application path independent of WebMCP. Use `supported` and
`registered` for status or optional affordances, not as a prerequisite for core
application behavior.
::

## The discovery flow

::steps{icon="i-lucide-list-ordered"}

### Controller starts

When `start()` is called, the controller checks for `document.modelContext`.

### Retry loop

If not found, it retries every 100ms for up to 3 seconds.

### Capability found

Once `document.modelContext` is available, `registerTool` is called with your
tool definition. On success, `supported` and `registered` become `true`.

### Timeout

If no capability is found after 3 seconds, `error` becomes a `ToolTimeoutError`
and `supported` remains `false`. The app continues working normally.

::

## What a tool should do

`inputSchema` describes the tool to the model. It is not runtime validation.
Every `execute` callback must validate its arguments and authorization before it
performs work. Use concise descriptions and outputs, mark read-only tools with
`readOnlyHint`, and treat `untrustedContentHint` and `exposedTo` as trust-boundary
decisions.

::warning{icon="i-lucide-shield-alert"}
**Validate everything.** `inputSchema` is for discovery, not security. Always
validate arguments inside `execute` before reading data or changing state.
::

The browser-facing wrapper includes discoverable metadata and `execute`. It does
not forward the library-only `formatOutput` or `onError` properties to WebMCP.

## Progressive enhancement

WebMCP is designed as progressive enhancement. Your app works normally without it,
and tools activate only when the browser supports the capability.

::important{icon="i-lucide-zap"}
**Optional by design.** The browser capability is detected at runtime. Your
regular UI remains the source of truth. WebMCP enhances your app — it doesn't
replace your existing functionality.
::
